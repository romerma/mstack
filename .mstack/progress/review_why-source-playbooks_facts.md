## Findings

1. `code-archaeology.md:32` - **this command hangs the agent that runs it.** `rg -l -i 'architecture.decision|adr' --glob '*.md'` has no PATH argument, so ripgrep takes the stdin form (`command | rg [OPTIONS] PATTERN`) and blocks forever when stdin is not a tty - which is exactly how a subagent runs it. Reproduced on ripgrep 15.2.0: killed by a 6s alarm (exit 142) with no path; exit 0 the moment `.` is appended or stdin is `/dev/null`. This is a playbook that stalls the investigation it is meant to start. Fix: `rg -l -i 'architecture.decision|adr' --glob '*.md' .` (line 33 is already safe - it takes `<file>`).

2. `code-archaeology.md:41-42` - **"the branch commits, which no longer exist" is false, and it costs the investigator the best artifact in the file.** Squash-merging removes the commits from the base branch only; GitHub keeps them on the PR and at `refs/pull/<n>/head` even after the head branch is deleted. Verified end to end on cli/cli#14095 (11 commits, squash-merged, branch 404s): `gh pr view 14095 --repo cli/cli --json commits` returns all 11, and `git fetch origin refs/pull/14095/head` fetches them locally with messages like "Stop claiming a human wrote the memory file" - precisely the per-step reasoning this page says is gone. It should say: the squashed commit on the trunk hides them, so pull them from the PR - `gh pr view <n> --json commits` (add `commits` to the field list on line 26), or `git fetch origin refs/pull/<n>/head` for the diffs. Note this error was inherited from pstack ("Squash merges eliminate branch history") and strengthened in the rewrite.

3. `telemetry.md:22-23` - **"Dashboards get edited in place, with no history" is wrong for both named tools, and it suppresses the one dated, authored telemetry artifact.** Grafana: "previous versions of your dashboard are never lost", with diff and restore. Datadog: "Preview, restore, or clone your dashboard's version history". Dashboard version history answers the exact question the page poses two lines earlier ("the panel you are looking at may not be the panel anyone looked at then"), and this text tells the investigator not to look. It should say: open the dashboard's version history and read the revision nearest the commit date; it is dated and attributed, like a commit.

4. `telemetry.md:19-21` - **"Most of these systems keep raw data for weeks ... if the code is a year old, the data that motivated it is gone" is wrong for Datadog metrics**, the first tool in the title and the source of every "magic number" this page is about. Datadog keeps metrics for 15 months. The weeks figure holds for logs and traces (Errors 15 days, Indexed spans 15-30 days), for Prometheus (`15d` default) and for Honeycomb (60 days). As written it will make an investigator skip a year-old latency graph that is still there. Split the claim: metrics are usually long-lived, logs and traces are not.

5. `chat.md:28-29` - **"DMs ... are not searchable. A known, permanent gap" is wrong for the DMs the agent can actually reach.** Slack search covers DMs the searcher participates in (`with:@person`). A Slack MCP holding a user token inherits that reach; only a bot token, and other people's DMs, are genuinely closed. Stated absolutely, this declares a gap where a search would have worked. Fix: "DMs you are not in are not searchable, and a bot token cannot search at all; your own DMs are - search them with `with:@person`."

6. `tickets.md:19-20` - **"'Done' is a workflow state a human clicked" is wrong for Linear by default**, and it discards a link. Linear's GitHub integration moves linked issues to Done on PR merge out of the box; Jira does the same through automation. So Done is frequently machine-set *by a merge*, which both weakens the "a human clicked it" framing and means the ticket is carrying a PR reference - the thing this whole investigation is trying to find. Fix: "Done may be a human click or a PR-merge automation. If it was the automation, the linked PR is on the ticket - follow it."

7. `error-tracking.md:25` - **"`resolved` is a button a human pressed. It is a marker, not a code change" is wrong twice.** Sentry resolves issues from commit/PR references shipped in a release, and has a project-level auto-resolve-after-N-hours setting; a resolved issue also auto-regresses if it recurs in a later release. The useful correction points the same way as finding 6: when the resolution came from the release integration, there is a commit attached to the issue. Fix: "`resolved` may be a human click, an auto-resolve timer, or a commit shipped in a release - check which. If a commit resolved it, that commit is your answer."

8. `documents.md:11-12` - **"Read the comment threads ... where the tool exposes them" needs the Notion caveat**, because the API does not expose them. Notion's list-comments endpoint "Retrieves a list of un-resolved Comment objects" - every settled thread, which is where the argument concluded, is invisible to an MCP client and visible only in the UI. This page's whole thesis is that the comments hold the tradeoffs, so the one tool-specific fact that defeats it belongs on the page. Same paragraph, `documents.md:23-24`: "the earlier revisions, both of which the clean final page removes" - the rendered page hides them, but Confluence retains every version with compare/restore and Notion keeps plan-bounded page history. Say "the page hides them; the history does not".

9. `telemetry.md:28-29` - **"Missing data plots as zero in many tools" is backwards for the tools named.** Datadog interpolates gaps by default for gauges (linear, up to 5 minutes) and leaves count/rate gaps empty (`.fill(null)`); zero-fill requires an explicit `default_zero()`. Grafana renders nulls as gaps. The real trap is the inverse of the one written: a short outage can be *interpolated away* into a healthy-looking line. As written it teaches the investigator to dismiss a genuine zero as a collector fault.

10. `code-archaeology.md:38-40` - **the `git blame` warning is correct but stops one line short of the fix.** Reproduced: a whitespace-only commit reassigns the line to the reformatter, and both `git blame -w` and `git blame --ignore-rev <reformat-sha>` restore the original author. The page tells the investigator to check the blamed commit by hand for a problem git will solve outright. Add `-w`, `--ignore-rev`, and `--ignore-revs-file` (repos that ship a `.git-blame-ignore-revs` have already listed their reformats for you).

11. `code-archaeology.md:16-17` - **`-G` is not the regex version of `-S`, and the comment on line 16 hides the difference.** `-S` matches only when the *number of occurrences* changes, so it misses in-place edits - changing a timeout from `30` to `5` inside an existing call is exactly the archaeology case and exactly what `-S` drops. The git man page carries the worked example. One clause each: `-S` for "when did this string appear or vanish", `-G` for "when did any line containing this change".

12. `chat.md:4` + `telemetry.md:19` - **the two files contradict each other on which source is most ephemeral.** chat.md calls chat "the most ephemeral source you have"; telemetry.md says telemetry keeps "raw data for weeks". A default paid Slack workspace keeps messages for the lifetime of the workspace, so the ordering is inverted. Combined with `chat.md:26-27` ("that date is **probably** the retention limit"), an investigator is being told to attribute silence to deletion under the one configuration where nothing was deleted. Fix: check the workspace's retention setting before naming retention as the cause, and drop the superlative.

13. `sources.md:40` - **"None of these sources reach rung 4" is right about *why* and understated about *what happened*.** As a claim about intent the cap is correct and well argued: you cannot execute a reason (`code-archaeology.md:52-54` says this best). But three of these playbooks return observations of the running system, and the ladder's own rungs 4-5 are "you ran it" / "you reproduced it in the running system". A verbatim re-runnable production query showing a code path serves 0.3% of sessions (`analytics.md:36-38`, capped at rung 2) is stronger evidence about live behaviour than "you pointed at the line", and a Sentry event is the running system failing. Understating evidence is the safe direction, but the sentence is stated as a property of the sources rather than of the claim. Scope it: "None of these sources can get a claim about *why* past rung 2." The per-file rung lines are otherwise defensible against `skills/router/references/evidence-ladder.md`; `incidents.md:39-41` is the sharpest of the eight.
